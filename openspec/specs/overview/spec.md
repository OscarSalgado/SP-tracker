## Purpose

A curated pipeline that ingests scientific articles (via link or PDF) and produces reproducible
per-article dossiers containing summaries, keyword classification, reusable simulation code,
synthetic/public datasets, and validation notebooks. It exists to make scientific results
independently reproducible without redistributing copyrighted source material.

## Domains

This system is organized into the following domains:

| Domain | Description | Spec |
|--------|-------------|------|
| Article | Extrae y filtra el contenido esencial de un PDF de artículo científico (abstract, introducción, métodos, resultados, conclusiones) para reducir el consumo de tokens al pasarlo a Claude. | [spec.md](../article/spec.md) |
| Synthetic-data | Provides a multi-degree-of-freedom (MDOF) dynamic model of high-speed elevator longitudinal vibration, assembling substructure mass/stiffness/damping matrices and deriving state-space and modal properties for reuse/reproduction of the article's analysis. | [spec.md](../synthetic-data/spec.md) |
| Validation | Enforces CONSTITUTION.md structural requirements for an article directory: required files, absence of source PDFs, presence of reuse code or justified absence, and taxonomy-compliant metadata. | [spec.md](../validation/spec.md) |
| Bibliography | Aggregates per-article metadata from the articles directory into a consolidated BibTeX-style references.bib file, enforcing required bibliographic fields. | [spec.md](../bibliography/spec.md) |

## Requirements

### Requirement: SystemCapabilities

The system SHALL provide the following capabilities:
- Per-article vertical slices (articles/<slug>/src/) rather than a shared simulation framework — each article's model, excitation, and solver code is self-contained
- Synthetic or public data only, generated in-repo (SyntheticElevatorDataGenerator), to avoid redistributing proprietary/copyrighted datasets
- PDF essence extraction is a separate preprocessing step (PdfEssenceExtractor) specifically to reduce LLM token consumption, not merely for storage
- Structural compliance (ArticleStructureValidator) and bibliography generation (BibliographyGenerator) are enforced by scripts run in CI rather than left to manual review
- Fixed-step RK4 integration was chosen for solving the state-space dynamics (RK4Solver) rather than an adaptive-step or library ODE solver — suggests a preference for reproducibility/determinism over solver sophistication
- CLI-first tooling surface (generate_bibliography.py, validate_article.py, extract_pdf_essence.py) with no HTTP API, reflecting the repo's role as an internal curation/reproducibility tool rather than a served application

### Requirement: DataFlow

The system SHALL process data through defined layers:

#### Scenario: StandardDataFlow
- **GIVEN** an incoming request
- **WHEN** the request is processed
- **THEN** data flows through: A user runs /vigilar-articulo with a URL or PDF -> PdfEssenceExtractor filters the PDF to essential sections (abstract/methods/results) to reduce token cost -> Claude produces summary + taxonomy classification -> reusable simulation code is authored per article (model assembly in ElevatorMDOFModel -> excitation signals from ExcitationGenerator -> ElevatorDynamicsSolverService assembles state-space matrices and drives RK4Solver -> SyntheticElevatorDataGenerator.generate_scenario produces synthetic time-series datasets) -> outputs (summary, code, synthetic data, notebook) are written into articles/<slug>/ -> ArticleStructureValidator checks the resulting directory against CONSTITUTION.md -> BibliographyGenerator aggregates metadata.yaml across all articles into references.bib -> CI workflow (article-pr-checks.yml) runs validation/checks as a merge gate. No database; the filesystem (articles/ directory tree) is the persistence layer.

## Technical Notes

- **Architecture Style**: Layered architecture with a per-article vertical-slice convention on top: a common ingestion/validation layer (scripts/, .github workflow gate) sits above per-article domain layers (articles/<slug>/src/) that each implement model -> excitation/data-generation -> numerical solver -> synthetic dataset stages. Cross-cutting concerns (bibliography aggregation, structural validation, PDF preprocessing) are centralized in scripts/ and enforced in CI, while each article's simulation code is self-contained and independently testable.
- **Security Model**: No runtime authN/authZ — this is a local/CI tooling repo, not a service. The relevant control is content governance, not access control: PDFs and full article text are never committed (copyright compliance, enforced by ArticleStructureValidator checking for absence of source PDFs), and any PR affecting articles/** must pass the CI gate before merge. Human confirmation is required (per CLAUDE.md) before adding new taxonomy keywords or pushing/opening PRs.
- **External Integrations**: Claude (article summarization/classification, invoked via the /vigilar-articulo command), GitHub Actions (CI gate on PRs touching articles/**), PDF source articles referenced only by source_url/DOI, never committed
